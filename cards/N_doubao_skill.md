# 豆包侧技能草稿：双 AI 多轮碰撞（PR 碰头循环）

> 用途：主人只给一个话题（如"去公园玩""上班"）。Claude 侧激活其技能后，生成一段提示词发给豆包；豆包收到后按本技能与 Claude 在同一个 GitHub PR 里多轮碰撞，主人只看最终结果。
> 本文件是豆包侧草稿，待 Claude 合并两边版本后定稿。

## 1. 触发语（Claude 生成、主人粘贴，豆包收到即激活）
固定前缀 **【碰头循环-豆包就位】**，字段缺一不可：
- 话题/目标：一句话。
- 仓库 owner/repo、PR 编号、Claude 工作分支、豆包交付分支、背景规则文件路径。
- 回合编号规则（如 T+日期-序号 T20261015-01）、总轮数上限。
- 硬时限（北京时间）。
- 评分表版本与硬门槛清单（如 G0/G1/G2/G3/G4/G5）。
- 回复格式、单条字数、长内容放文件的约定。
- 凭证：不写令牌；由豆包侧环境预置只读令牌文件（路径由主人环境配置），豆包只在命令行 `cat` 使用，**禁止写进任何评论、文件、commit、回复正文**。
豆包若发现字段不全（尤其缺轮数上限/硬时限/分支），先回报"缺哪几项"，不猜。

## 2. 首次启动（只做一次）
1. 用 contents API 读 PR 描述（pulls/N）和背景规则文件（带 `?ref=分支`，中文路径必须 URL 编码；Accept: application/vnd.github.raw）。
2. 确认豆包交付分支存在：不存在则基于默认分支最新 commit 创建（PUT refs/heads/...）。
3. 建定时任务：cron 整点触发（表达式 `0 * * * *`），带 deadline=硬时限；建前先 list_cron_jobs 防重复；**禁止嵌套创建**（任务运行中不再建新任务）。
4. 向主人回报：已就位、首轮开始。

## 3. 每一轮标准动作
1. 轮询：整点触发后进入 while 循环，每 120 秒查一次 pulls/N（state）与 issues/N/comments（per_page=100）。
2. 识别：找含 `[给豆包]` 且带回合编号的评论；检查是否已存在以 `[给Claude] 回复 T编号` 开头的评论；已回复跳过；只处理发给豆包的，不碰发给 Claude 的。
3. 读任务：读本轮引用的 board 文件（Claude 分支），严格按当轮要求做；创作/盲评/调研分开交付。
4. 盲评规则：不知道作者时不讨论样本来源；每行 veto 先行；无成片的指标（秒数、完播率、转折点）一律"无数据"，不估算。
5. 调研规则：事实必须实际打开页面（web.fetch 或 curl）；打不开写"未打开"，凭印象=违规；不编链接、数字、官方说法；优先政府/博物馆/官媒/百科，遇 robots 拦截（如携程）换源。
6. 产出：文件放豆包交付分支（PUT contents；已存在先 GET 取 sha 再 PUT）；评论里贴 blob 链接。
7. 回复（格式见第 4 节），POST 后重新拉评论读回，确认"[给Claude] 回复 T编号"配对存在，才算完成。
8. 本轮无新任务：不发声、不评论、不创建任何任务，sleep 120 继续。

## 4. 回复格式
- 开头固定：`[给Claude] 回复 T编号：`
- 每条按：**结论（一句）→ 依据（只写真正打开过的链接，无依据写"无依据"，打不开写"未打开"）→ 把握（高/中/低）→ 与 Claude 立场的关系（同意/反对/补充）**。
- 单条 ≤1200 字（去链接后计数）；超长分 (1/2)(2/2)；长内容放文件，评论只贴链接+摘要。
- 不写令牌、密码、账号、姓名、手机号。

## 5. 自轮询机制（已实测）
- 一个 cron 整点任务（最小触发间隔实测为 1 小时）；任务体跑 bash while：`end=$((SECONDS+3000))`（约 50 分钟），到点安静退出等下一次整点。
- 脚本退出码约定：0=本窗口到点无新事；7=发现 [定稿] 或 PR 已关闭（调 list_cron_jobs 按标题找 ID→delete_cron_job）；8=发现新任务（退出后立即处理）。
- 长轮询必须后台运行（run_in_background），再用 TaskOutput 阻塞观察；前台命令有 5 分钟超时。
- 脚本写好先跑一帧验证语法（曾因漏右括号 exit 2）。

## 6. 停止条件（任一满足即收尾）
1. 任意评论或背景文件出现 `[定稿]`；2. PR state != open；3. 到达硬时限（北京时间）；4. 已打完约定总轮数且无后续。
收尾动作：删除本 cron 任务；向主人汇报各轮产出文件清单与最终结论。

## 7. 必须标"未核实/无数据/未打开"的清单
- 链接打不开、平台需登录、被 robots 拦截：标"未打开"，不引用其细节。
- 平台不公开的指标（完播率、秒级节拍、转折秒数）：标"无数据"，不写估值。
- 单一来源、口径冲突（如"千年古樟"与"百年古樟26棵"）：两种口径并列，注明来源，不替对方裁决。
- 盲评阶段对样本来源的猜测：不写。

## 8. 豆包最容易犯的错与防线（按本轮实测）
1. **编链接/凭印象写事实**→ 每条链接必须实际打开；写文件时逐条附"已打开/未打开"。
2. **估算不公开数据**→ 评分与秒数留空写"无数据"，宁可不写。
3. **回复格式漂移**→ 开头模板+四要素+字数计数（脚本打印字符数）。
4. **盲评夹带作者信息**→ 先盲评再对来源；jsonl 里不写来源。
5. **文件覆盖冲突/丢失**→ PUT 前先 GET 取 sha；推送后检查 HTTP 201。
6. **评论发了但没配对**→ POST 后重新拉评论，按编号确认配对。
7. **长轮询占前台被超时切断**→ 后台+TaskOutput；脚本独立成文件。
8. **/tmp 命名空间重置**→ 写文件与推送/POST 放进同一条 heredoc 命令，或先 ls 确认。
9. **重复/嵌套定时任务**→ 建前 list_cron_jobs；运行中绝不 create。
10. **凭证泄露**→ 令牌只在命令行 cat；正文、文件、commit 均不得出现。
11. **计算/数量失误**→ 数量、时长、字数用工具算，不口算。
12. **擅自扩题/换格式**→ 只做当轮 board 文件点名的交付物，题型、配图、字段不擅改。

## 9. 与 Claude 侧技能的接口约定（建议）
- 共用：回合编号、评分表版本号、硬门槛清单、分支命名、文件命名（A/B/C…字母顺序，jsonl 一行一个）。
- 每轮 Claude 负责：抽卡（公开种子）、封存哈希（SHA-256）、组织全新评委盲评、把结果写 board 文件。
- 每轮豆包负责：独立盲评、联网核实、创作/反方、文件落豆包分支。
- 双方在评论里只用统一格式；主人不介入，只在最终轮看结果与是否做试播镜头。
